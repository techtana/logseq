# Who can reach the self-hosted sync server

Checked 2026-11-22 against the live VM metadata, the Google Cloud audit log and the
server itself. This fork syncs DB graphs to a self-hosted server instead of
`api.logseq.io`; each client sets the custom sync server URL in Settings.

This page is the Logseq side of the owner's "Tailscale is the single front door"
design (home-digital-twin repo,
`docs/design/plans/2026-11-22-tailscale-front-door.md`). Placeholders: `<tailnet>`
is the tailnet name, `<project>` the Google Cloud project, `<owner>` the owner.

## The setup

- A Compute Engine VM `logseq-sync` (e2-micro, Debian 12) with **no public IP**.
  It reaches the internet only outbound, through Cloud NAT.
- The sync server is the Docker image `ghcr.io/yshalsager/logseq-selfhost-sync`
  (it packages this repo's Node adapter, `deps/db-sync`). It listens only on
  `127.0.0.1:8787`.
- **Tailscale Serve** publishes it as `https://logseq-sync.<tailnet>.ts.net`, with
  Tailscale's HTTPS certificate. The VM is a tailnet device tagged `tag:logseq`.
- Admins get in with SSH through Google IAP (`gcloud compute ssh logseq-sync
  --tunnel-through-iap`), not through Tailscale. OS Login is on and project SSH
  keys are blocked.
- A GCE startup script, generated by `deploy.sh` (kept outside this repo), sets
  all of this up on every boot.

## Two locks on the notes

A request has to get past both locks:

1. **Tailscale: is this device on the tailnet, and does the policy let it reach
   `tag:logseq` on port 443?** A device off the tailnet can't even find the
   server.
2. **The sync server: is there a valid Logseq account login, and is that
   account a member of the graph?** The server checks each request's token
   against Logseq's Cognito pool (`COGNITO_ISSUER`, `COGNITO_CLIENT_ID`,
   `COGNITO_JWKS_URL` in its `.env`; see `deps/db-sync/src/logseq/db_sync/worker/auth.cljs`),
   then checks graph membership. `DB_SYNC_ALLOW_UNVERIFIED_JWT_CLAIMS`, which
   would loosen this check, is not set. Checked from a tailnet device:
   `GET /graphs` with no token returns `401`, and `/health` returns `{"ok":true}`.

So Tailscale is **not** the only lock. Still:

- Any Logseq account that gets past lock 1 can sign in and create graphs of its
  own on the server. It can't read the owner's graphs. Lock 1 is what keeps
  strangers off the server's disk.
- An admin token (`DB_SYNC_ADMIN_TOKEN`, header `x-db-sync-admin-token`) passes
  the graph-membership check. It is generated on the VM, stored at
  `/srv/logseq/secrets/admin_token` (mode 700), and never leaves the VM.
- Graph contents are stored readable on the server unless the graph uses sync
  encryption (`docs/adr/0003-optional-sync-graph-encryption.md`).

## Tailnet policy for `tag:logseq`

**Not yet recorded.** AI sessions don't get tailnet admin rights, so the live rules
have to be read by the owner in the admin console. If the policy is still
Tailscale's default, every tailnet device may reach the notes on every port.

The target is in [tailnet-policy.reference.hujson](tailnet-policy.reference.hujson):
only `group:owner` may reach `tag:logseq`, and only on `tcp:443`. That file is a
redacted reference copy. **The admin console is the only live copy.** Nothing
syncs git to Tailscale.

Removing the default allow-all rule affects every app on the tailnet, not just
Logseq. Make that change together with the rules for the other apps in the
front-door plan, or devices will lose access to them.

## How the VM gets its Tailscale key

- `deploy.sh` puts a Tailscale auth key into the Secret Manager secret
  `logseq-ts-authkey` and grants access to it only to the VM's own service
  account, `logseq-sync-vm`. That account has no other roles beyond writing
  logs and metrics.
- On boot, if Tailscale isn't already running, the startup script reads the
  secret with the service account's token and runs `tailscale up --auth-key=...`.
  The script has no `--advertise-tags`, so `tag:logseq` comes from the key itself
  (a tagged key).
- After the first join, `deploy.sh` deleted the secret. The audit log shows it
  created on 2026-10-05 02:20 and deleted at 02:23 UTC. No key is stored in the
  project now, and none has ever been in this repo or in instance metadata.
  (Instance metadata would be the wrong place anyway: anyone who can view the
  VM in the project can read it.)
- Because the device is tagged, Tailscale owns it, not a person. It doesn't
  expire when someone leaves. Tagged devices have key expiry off by default.
- The device's login lives in Tailscale's state on the boot disk. If that disk
  is replaced, the VM can't rejoin on its own: the startup script stops with an
  error at the join step until `deploy.sh` is re-run with a new key.

Not visible from Google Cloud: whether the key was single-use or reusable, and
whether it has expired. The owner checks this in the admin console (see below).

## Risks to keep in mind

- **The VM is a single point of failure.** From 2026-11-18 to 2026-11-20 an
  automatic kernel update (Debian 6.1.0-55, an ext4 bug) hung all disk writes
  after the 04:00 UTC auto-reboot. Tailscale showed the device offline while Google
  Cloud still said RUNNING, and sync was down until the kernel was replaced.
  Unattended upgrades with automatic reboot are still on.
- **The second lock lives in a third-party image.** Compose pulls
  `logseq-selfhost-sync:latest` on every boot and every Sunday at 03:30. An
  upstream change could change or drop the token check without any change
  here. Pinning the image by digest would stop that, at the cost of manual
  updates.
- **The dashboard's Tailscale proxy (front-door plan) is undecided.** It may
  share this VM, so one outage would take down both apps, or get its own VM.
  Don't build it here until that is decided.
- The project's default Compute Engine service account still has `roles/editor`.
  The sync VM doesn't use it, but anything that later runs as that account
  would get Editor on the whole project.

## Steps only the owner can run

1. **Read the current tailnet policy.** Admin console → Access controls. Note
   any rule whose `src` or `dst` is `*`, and anything that names `tag:logseq`.
2. **Apply the `tag:logseq` rule.** Copy the `groups`, `tagOwners`, `grants` and
   `tests` entries from `tailnet-policy.reference.hujson` into the console
   policy, putting your real sign-in where it says `<owner-login>`. Remove the
   allow-all rule only together with the other apps' rules (see above). Tailscale
   runs the `tests` block on save and refuses a policy that fails them.
3. **Check the key and device.** Settings → Keys: if an auth key for the Logseq VM
   is still listed, revoke it. Revoking doesn't disconnect the VM, which is
   already joined. Machines → `logseq-sync`: it should show `tag:logseq` and
   "Expiry disabled".
4. **Check Serve's prerequisites stay on.** DNS page: MagicDNS and HTTPS
   Certificates. Serve fails without them.
5. Optional: pin the sync image by digest in `deploy.sh`, and remove
   `roles/editor` from the default Compute Engine service account if nothing
   else uses it.

To check from any tailnet device afterwards:

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://logseq-sync.<tailnet>.ts.net/graphs
```

Expect `401` from an allowed device, and a timeout from a device the policy
blocks.
